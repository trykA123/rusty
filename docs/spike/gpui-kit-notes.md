# gpui-kit 0.7.3 notes for Ferrite (atom S1, plan P2)

Paths: CR = ~/.cargo/registry/src/index.crates.io-*/. Prototype = <worktrees>/rusty-gpui-b-variants/spikes/gpui-b-variants (PT).

## 1. Dependency, re-exports, bootstrap
`gpui-kit` is a facade. `gpui_kit::*` is GPUI itself, which is the crate `gpui-pre` 0.3.9, a snapshot republish of Zed's gpui (gpui-kit-0.7.3/Cargo.toml:404-407, `package = "gpui-pre"`, `=0.3.9`). Layers: `gpui_kit::platform` (gpui-pre-platform), `base` (gpui-base 0.7.3), `component` (gpui-component 0.7.3), `assets` (gpui-kit-assets) (gpui-kit-0.7.3/src/lib.rs:1-20). Default features: `component`, `assets`. Others: `test-support` (dev-dep only), `inspector`, `profiler`, `gpui-fast` (alternative backend), `speech`, `decimal`, tree-sitter-*. No direct `gpui` dep is needed.
Minimal bootstrap (PT/src/main.rs:160-193): `gpui_kit::application().with_assets(..).run(|cx| { gpui_kit::init(cx); /* add_fonts, bind keys */ gpui_kit::open_window(WindowOptions{..}, cx, |window, cx| cx.new(|cx| Workspace::new(..))) })`. Prototype Cargo.toml pins `gpui-kit = "=0.7.3"`, edition 2024, `[workspace]` empty. The `actions!` macro is re-exported (lib.rs:35-60) so `#[derive(Action)]` works without a `gpui` crate name.
Risk: GPUI is a third-party snapshot of Zed (not zed's git crate); APIs follow Zed at commit 93d7456 (gpui-pre-windows Cargo.toml:23). Pin exactly; every kit bump moves GPUI too. Edition 2024 needs a recent stable Rust.

## 2. Virtual list and table
- `uniform_list(id, count, |this, range, window, cx| -> Vec<impl IntoElement>)` from GPUI (PT/src/file_list.rs:74; gpui-pre-0.3.9/src/elements/uniform_list.rs:22). All rows share one height (measured from the first item). Only the visible range is rendered, so 100k rows is O(visible). Scroll: `UniformListScrollHandle` + `.track_scroll(&h)`, `h.scroll_to_item(ix, ScrollStrategy::Nearest|Top|Bottom|Center)` (PT/src/pane.rs:48-51). PT renders 100k generated rows this way (pane.rs `entry()` generates on demand).
- Variable height: `v_virtual_list(view_entity, id, Rc<Vec<Size<Pixels>>>, |view, range, window, cx| Vec<R>)` (gpui-base-0.7.3/src/virtual_list.rs:139; re-exported at gpui-component-0.7.3/src/virtual_list.rs:2). Needs a per-item size vec, so 100k rows costs a 100k-entry Vec and rebuilds on change (compares `items_sizes != item_sizes`, line ~477). Handle: `VirtualListScrollHandle::scroll_to_item(ix, strategy)` (line 107), `scroll_to_bottom`. `h_virtual_list` for columns.
- Table: `gpui_kit::component::table::{DataTable, TableState<D>, TableDelegate, Column}`. Delegate trait: `columns_count`, `rows_count`, `column`, `render_th`, `render_tr`, `render_td`, `perform_sort`, `context_menu`, `move_column` (gpui-component-0.7.3/src/table/delegate.rs). Rows use `uniform_list` internally (fixed height), columns use a horizontal VirtualList (table/state.rs:19-20, 258). API: `TableState::new(delegate, window, cx).sortable().col_resizable().col_movable().row_selectable()`, `scroll_to_row(ix, cx)` (state.rs:413), `selected_row()`, `set_selected_row`, `visible_range()`; `DataTable::new(&state).stripe(true).bordered().scrollbar_visible(v,h)` (data_table.rs:104-135). Keyboard up/down moves selection and scrolls (state.rs:513).
- Scrollbar: `gpui_base::Scrollbar` (reachable via `gpui_kit::base`) with `Scrollbar::vertical(&handle)`; `ScrollbarHandle` is implemented for `ScrollHandle`, `UniformListScrollHandle`, `ListState`, `VirtualListScrollHandle` (gpui-base-0.7.3/src/scrollbar.rs:69-130, 815+). Thumb colours come from the theme (`scrollbar_thumb`, PT tokens/kit.rs:42-44).
- Also `list::ListState/List` (searchable, grouped, IndexPath) at gpui-component list/list.rs; it has `scroll_to_item`.
Risk: PT does NOT use DataTable; it hand-builds rows (good for file-manager control: marks, cursor, pill selection). DataTable has built-in stripe, sort, resize, but single-selection model; marks/multi-select would be custom. Open issue #3513 (scrollbar drag range excludes list padding) and #3474 (Diff stalls) exist upstream. Three panes = three independent handles/lists; no shared state needed. Rows must be built cheap (generate `Entry` lazily as PT does).

## 3. Dock
`gpui_kit::component::dock` re-exports gpui-base dock: `DockArea`, `DockSkin` (chrome), `DockLayout`, `PaneTree`, `TabGroup`, `PanelRegistry`, `register_panel`, `Panel`/`BasePanel` traits (gpui-component-0.7.3/src/dock/mod.rs:1-60). Build: `DockSkin::dock_area("id", version, window, cx)` -> (area, skin); `DockLayout::tabs().panel_view(handle, cx)`; `area.set_center(layout, window, cx)`; panel styles via `skin.set_panel_style(PanelStyle::TabBar, cx)` (gpui-kit tests/dock.rs:77-90). Splits are "stack" nodes with axis + sizes; tabs; left/right/bottom docks with open/size; zoom (ToggleZoom action); drag tabs between groups (tests/dock.rs:117).
Serialisation: `DockArea::dump(cx) -> DockAreaState` and `DockArea::load(state, window, cx) -> Result` (gpui-base-0.7.3/src/dock/dock_area.rs:895, 817). `DockAreaState` is serde: `{version: Option<usize>, center: PanelState, left_dock/right_dock/bottom_dock: Option<DockState{panel,placement,size,open}>}`; `PanelState{panel_name, children, info}`; `PanelInfo` = `stack{sizes,axis}` | `tabs{active_index}` | `panel(json)` (dock/state.rs:9-85). Restore rebuilds panels through `PanelRegistry` by `panel_name`; unknown panels become placeholders that keep their state. 0.7.1 added `DockArea::set_split_sizes`.
Risk: Ferrite's three panes fit a horizontal stack of 3 tab groups. Panels must be registered and have serialisable `panel(json)` info; entity-bound state (cwd, sort) goes in that json. Dock is skinned in gpui-component styling; PT used its own pane chrome, so we may only need the layout/persist half (`DockArea` with no `DockSkin` renders no chrome, mod.rs:15-17).

## 4. Theme format
Runtime theme is `gpui_kit::component::theme::Theme` (global). PT sets colours directly: `KitTheme::change(mode, None, cx)` then `KitTheme::update(cx, |kit| { kit.colors.background = ..})` (PT/src/tokens/kit.rs:1-54). Oklch helper `theme::oklch(l, c, h)` (PT tokens/mod.rs:5, 148).
File format: `ThemeSet{name, author, url, themes:[ThemeConfig]}` (gpui-component-0.7.3/src/theme/schema.rs:20-75), JSON, loaded by `ThemeRegistry::load_themes_from_str` or `ThemeRegistry::watch_dir(dir, cx, cb)` (theme/registry.rs:98,151). `ThemeConfig` keys: `is_default`, `name`, `mode` (light|dark), `font.size`, `font.family`, `mono_font.family`, `mono_font.size`, `radius`, `radius.lg`, `shadow`, `colors{}`, `highlight`. Colour values are hex, `#rrggbbaa`, or palette names like `neutral-100`, with `/alpha`. Schema file `.theme-schema.json` is referenced by `$schema` at github.com/longbridge/gpui-kit (raw/refs/heads/main/.theme-schema.json); it is NOT in the crate. Reference file: gpui-component-0.7.3/src/theme/default-theme.json (keys derived from `ThemeConfigColors`, schema.rs).
Token map (dotted keys):
- bg -> `background`; text -> `foreground`; muted -> `muted.foreground`; surface -> `list.head.background`/`table.head.background`/`popover.background`/`secondary.background`; line -> `border` (and `input.border`, `table.row.border`); accent -> `primary.background` (+`ring`); selection (row) -> `list.active.background`/`table.active.background` (+`.border`); zebra -> `list.even.background` / `table.even.background` (used when `DataTable::stripe(true)`); hover -> `list.hover.background`/`table.hover.background`; text selection -> `selection.background`; scrollbar -> `scrollbar.background`, `scrollbar.thumb.background`, `scrollbar.thumb.hover.background`; tabs -> `tab.*`, `tab_bar.background`.
Risk: our extra tokens (folder, kind colours, mark) are app-level, so keep our own `Theme` struct (as PT does) and only push the subset into the kit via `KitTheme::update`. Two theme systems to keep in sync.

Enable `gpui-kit = { features = ["test-support"] }` in dev-dependencies. Use `#[gpui_kit::test] async fn t(cx: &mut TestAppContext)` (not `#[test]`). Ext traits `gpui_kit::test::{TestWindowExt, TestAppContextExt, TestSupportExt, ElementSnapshot}` (gpui-kit-0.7.3/src/test.rs:25-50): `window.render_frame(cx)`, `find(id)`/`try_find`, `within(scope)`, `click`, `click_at`, `right_click`, `double_click`, `hover`, `scroll`, `drag_to`, `press("down", cx)`, `input("text", cx)`, `cx.wait_for(handle, timeout, |window,_| ..).await`. Elements opt in with `.test_support()` before `.track_focus`. Example that opens a headless window, clicks, asserts state: gpui-kit-0.7.3/tests/dock.rs:77-116. Key press + table selection assertions: tests/collections.rs:49-135 (`window.press("down")`, `TableSelection::Row(3)`). Risk: tests need the native test platform (works on Linux/Windows CI per TESTING.md; pixel `rendering` target is macOS-only). uniform_list rows need `.id()` and `.test_support()` to be findable. Perf of 100k rows must be measured separately.

## 6. AccessKit
GPUI integrates `accesskit` 0.24 (CR has accesskit-0.24.1, accesskit_windows-0.34.0, accesskit_unix/atspi). Windows: `accesskit_windows::Adapter` created in `a11y_init` (gpui-pre-windows-0.3.9/src/window.rs:1080-1104); Linux X11/Wayland also wired. macOS is not confirmed in this review (not searched). Guide: gpui-pre-0.3.9/src/_accessibility.rs. A node is exposed only if the element has an id and a role: `div().id(..).role(Role::ListItem)`. Table parts: Role::Table/Row/Cell with a tree update (gpui-base-0.7.3/src/table.rs:141-372); gpui-component `List` uses Role::List/ListItem (list/list.rs:492, 670); DataTable rows set Role::Row (table/state.rs:2057). `uniform_list` itself emits no a11y role (no a11y in elements/uniform_list.rs), so our custom file rows must set `.role(Role::ListItem)` (or Row/Cell in a Table), and a label, themselves. Reading the tree: `Window::debug_a11y_tree_json() -> Option<String>` (gpui-pre-0.3.9/src/window.rs:7011), and `ElementSnapshot` exposes label/value/selected/focused from the native a11y properties (TESTING.md). Upstream issue #3381 (empty UIA Name for Checkbox without label) shows Windows UIA is exercised.
Risk: only visible rows exist in the tree (virtualised), so screen readers see no total count unless we add Table role with row_count/set-size; unverified.

## 7. Windows build needs
- Target `x86_64-pc-windows-msvc`; MSVC build tools and Windows SDK. Windows crate deps: `windows` crate with Direct3D11, DirectComposition, DXGI, DirectWrite (gpui-pre-windows Cargo.toml:150-175). No features required (gpui-pre README: "Windows - no features are required").
- Release builds (no debug_assertions) compile HLSL with `fxc.exe` in build.rs (build.rs:4-11, 30-140): found via `GPUI_FXC_PATH`, `where.exe fxc.exe`, or latest Windows SDK bin; panics "Failed to find fxc.exe" otherwise. So the Windows 10/11 SDK is required for release builds. Debug builds skip this (shaders compiled at runtime; not verified).
- Renderer: D3D11 device, feature levels 11.1/11.0/10.1 (directx_devices.rs:160-166), BGRA support, swap chain `CreateSwapChainForComposition` with FLIP_SEQUENTIAL (directx_renderer.rs:1317-1321) i.e. DirectComposition; env `GPUI_DISABLE_DIRECT_COMPOSITION` turns it off (directx_renderer.rs:26, 135).
- Minimum OS: Windows 10 1703+ (DirectWrite code comment, direct_write.rs:172-173, 1525). Practically Windows 10/11.
- Manifest: kit feature `gpui-fast` uses `windows-manifest-provided-by-host`; gpui_platform enables `windows-manifest` (gpui-pre-platform Cargo.toml:110). Not studied further.
- Linux-side facts (our host): Cargo.lock shows `gpui-pre-linux`/wgpu; PT builds on Linux already.

## 8. Windows issues and GPU adapter selection
Code: `get_adapter` loops `dxgi_factory.EnumAdapters(adapter_index)` and returns the first adapter for which `D3D11CreateDevice` succeeds (gpui-pre-windows-0.3.9/src/directx_devices.rs:106-137). The factory is an `IDXGIFactory6` but `EnumAdapterByGpuPreference` is NOT used, so there is no way to prefer the low-power GPU through GPUI; order is whatever DXGI enumerates (adapter 0 is normally the one driving the primary output, which on a hybrid laptop is often the iGPU). There is no env var or option for adapter choice in the crate (grep of env::var found only GPUI_DISABLE_DIRECT_COMPOSITION, GPUI_FXC_PATH). Workaround: Windows Settings > Graphics per-app preference ("Power saving" / "High performance"), which changes which GPU DXGI returns first; or patch/fork. Device loss is handled (`WM_GPUI_GPU_DEVICE_LOST`, events.rs:29). `gpu_specs` reports software adapters (WARP flag) but does not exclude them (directx_renderer.rs:823-828).
Zed history: #39263 "First GPU is selected, rather than the best" (closed 2025-10-10), #36798 integrated GPU used instead of dedicated (closed 2025-09-18). Whether this snapshot contains those fixes: the code above still picks the first working adapter, so no preference logic is present.
gpui-kit release notes (github.com/longbridge/gpui-kit/releases): v0.7.3 (12 Oct 2026): single manifest with gpui-fast on Windows, DataTable header height + row count fixes, Dock focus fix, DataTable sort button label. v0.7.1 (5 Oct): Windows native speech, DataTable keyboard focus, `DockArea::set_split_sizes`. v0.7.0 (28 Sep): dock and accessibility improvements. No DirectX/GPU items in any of the three. Open issues of note: #3513, #3474, #3381 (UIA name), #3168 (native GPU surface seam). Issue search "windows" (118 matches) returned only 2 labelled-windows, both closed, neither GPU related; I did not read bodies.
