# Retention backend

D65's backend is available in `rusty-core::retention`, `rusty-store::RetentionCatalog` and the `rusty-retention` service crate. Development launches with `--experimental-retention` use it when the independent delete or Copy/Move setting is enabled. Ordinary launches ignore both keys. Both settings default to false. Bounded maintenance runs after retained jobs. Recently deleted, general user undo, periodic scheduling and terminal metadata pruning remain open.

## Public service

Create `Vault` with an already opened profile `Db`, the same profile data directory and a filesystem provider. Application callers must finish P35 preflight first and keep its database access lease. `Vault` owns a read/write `retention.lock` for its lifetime; another engine using that profile fails to acquire ownership. The SQLite connection closes before the engine lock is released.

`capture(CaptureRequest, RetentionRun)` preserves one file, link or entire folder tree. Requests specify the source, retention policy, UTC creation time in milliseconds and optional job owner. The result identifies a durable catalog entry. `restore(RestoreRequest, RetentionRun)` returns it to an explicitly selected vacant location on the same volume. `purge(id, RetentionRun)` removes a verified retained tree. `reconcile(id, RetentionRun)` resolves an interrupted phase or resumes a previously requested purge.

Operations are synchronous and must run on a worker when integrated with the application. `RetentionRun` supports cancellation and reports visited paths. Progress callbacks and full-tree verification run outside catalog write transactions. Other SQLite connections can write history and viewer memory while a retained operation pauses. Callbacks must not reenter the same Vault. Catalog reads use increasing identifiers and a requested page size of 1–1000 entries.

## Application activation

Launch with `ferrite --experimental-retention --profile <development-profile>`. The flag must match the already running instance for that profile; a mismatch is refused. Then set `[retention] retain-deletes = true` to preserve ordinary delete roots. Set `retain-overwrites = true` to preserve previous file/link versions replaced by Copy or Move. Settings validate the 1–7 day retention interval, volume cap and minimum free-space threshold. Unsupported providers and unavailable journals refuse these operations. After retained jobs finish, a bounded worker pass applies the current validated quota and minimum-free-space settings. Each saved version keeps its original expiry. A completing job protects its own entries from that maintenance pass while their bytes still count toward quota. Invalid or unavailable current settings defer maintenance.

Removing the flag does not delete retained folders or run maintenance. Existing retained bytes remain on disk, including after their recorded expiry. Private-path and catalog protection apply only with the experimental flag. Without it, ordinary operations can move, rename, recycle or remove leftover retention and holding folders, as on main. Re-enable the flag with the same profile to resume experimental retention and its bounded maintenance after retained jobs. Default mode does not query the catalog to protect ancestors outside those reserved paths; cross-mode coordination is outside this experimental feature's guarantees.

Retained deletes store root intents before capture. Cancellation or startup rollback restores only matching owned payloads; ambiguous paths remain pending. Retained writes store a distinct typed plan and identity proof before each overwrite. Parallel copy workers defer placement to the logging thread. Retained copies use per-job temporary namespaces and journal parent/mount intent before exclusive creation. The created handle identity must be durably acknowledged before data transfer. Failed/cancelled jobs and startup remove only matching proved temporaries in the original scope; replacements and unknown files remain pending with their paths. Windows uses native CopyFile2 to preserve alternate streams and STOP to leave interrupted files available for checked cleanup. Completion refuses unretired temporary evidence. Placement uses atomic no-replace renames and never falls back to permanent replacement.

`adopt_job(AdoptJob, RetentionRun)` adopts proved A8 `.ferrite-held-*` payloads in place. V2 records name one original file/link; several entries can share a holder. Restore and purge leave the shared holder until empty. V1 delete records still use a fixed `payload` child. Paths retain the existing lossless text encoding.

The adoption transaction checks complete durable proof coverage, plan/policy consistency and contiguous completed step sequences. It inserts Ready records, finishes the owner and removes terminal undo evidence atomically. Failed or cancelled writes retain already held versions; successfully returned originals are acknowledged after identity checks and empty-holder cleanup. Startup returns proved held bytes when the original target is absent. Successful retained-write recovery finishes as Failed, preserves any remaining previous versions and clears terminal undo evidence. Unproved or changed paths stay pinned and restore-pending for manual inspection. Automatic Copy/Move rollback awaits the general undo stage.

Only launches with `--experimental-retention` acquire user mutation leases. In that mode, ordinary copies, editor saves and creation hold shared leases. Rename, recycle, folder removal, retained operations and startup recovery take exclusive leases before guards and tree scans. Structural operations can queue behind a long copy; queued jobs remain cancellable. Saves, creation and startup have a three-second lock deadline. Retention policy parsing is limited to the retention table and relevant experimental operations. Private retention/holding folders are protected through aliases and parent relocation. Leases stay held through completion and adoption. The lock uses a private reserved directory beneath the OS account home on Unix or the native LocalAppData folder on Windows. It does not change with session environment overrides. Without the flag, jobs, saves, creation, Undo and startup recovery acquire no user mutation lease. Their retention guards skip profile-directory canonicalization and catalog access. Default mutation paths do not resolve or refuse private retention names. With the flag, mutation guards first check the V7 live index for any live entry; an empty catalog skips path filtering. Nonempty catalogs read live container paths without decoding manifests or terminal records. Proof-bearing journal rows never enter legacy stamp-only recovery or cleanup, including damaged job kinds.

## Policy

`RetentionPolicy::new(days, max_volume_bytes, min_free_bytes)` requires 1–7 days and a positive cap. Validated defaults are three days, a 1 GiB logical-byte cap and 256 MiB minimum free space. Retention remains opt-in. `select_purge` validates the supplied inventory and rejects duplicate identifiers.

Selection considers one observed volume at a time. It chooses expired entries first, then the oldest eligible entries until the logical-byte cap is met. Running, restore-pending or unverified owning jobs pin entries; preparing, restoring, purging and conflicted entries also remain ineligible. Pinned bytes still count toward the quota, and the result reports when the quota cannot be met safely.

Logical sizes include each retained file/link path. They can overcount hard links and sparse files. Physical free space is never inferred from those sizes. Low space selects one additional entry when no expiry/quota choices already exist; the caller must observe free space again after deletion before selecting further entries.

## Bounded maintenance

`maintain_volume(MaintenanceRequest, RetentionRun)` loads validated compact summaries instead of keeping complete manifests in memory. Inventory is limited to 100,000 live entries; each pass permits 1–256 purges and a separately bounded terminal-container cleanup batch. The app requests at most 32 of each after a retained job, while holding its existing mutation leases.

The provider observes available physical bytes on the selected directory's volume. Identity and mount checks surround each observation. The service resumes interrupted Purging entries, then applies expiry/quota/low-space policy, remeasuring after every committed purge. Unsupported observations, unavailable volumes, replaced payloads and cancellation stop the pass. Reports count actual remaining logical bytes and unresolved limits. Maintenance errors preserve the completed user operation's state.

Terminal cleanup is acknowledged only when the owned container is absent or safely removed. Missing container identity never authorizes deleting an unknown folder or acknowledging one that still exists. Persisted attempt rounds prevent one occupied or failing holder from starving later cleanup. Catalog snapshots remain available after acknowledgement.

## Filesystem boundary

Capture creates a new sibling `.ferrite-retained-PID-TIME-SERIAL` container and renames the source into its `payload` child. It copies no file content. Windows sets the hidden attribute through an identity-checked directory handle after durable ownership registration, before moving content. The native implementation follows [Microsoft FILE_BASIC_INFO](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_basic_info). Containers are exclusively created; existing names are never adopted or replaced. Trees containing reserved retention folders are refused to avoid relocating an existing catalog's storage.

Providers must explicitly support `ProviderOps::rename_atomic` and supply file and mount identities. The default implementations refuse retention. Linux uses native `renameat2` with `NOREPLACE`, with no check-then-rename or hard-link fallback. Windows uses the existing `MoveFileExW` operation without `REPLACE_EXISTING`. Other platforms and unsupported filesystems fail safely. The ordinary job engine's rename behavior is unchanged.

Linux checks `statx` mount identity separately from device/file identity before traversing a folder. This also excludes same-device bind mounts; the kernel documents the separate `stx_mnt_id` field in [statx(2)](https://man7.org/linux/man-pages/man2/statx.2.html). V1 operations observe current mount identities. V2 overwrite proofs also persist the original mount identity; a changed mount after restart keeps the job pending for manual recovery. Windows treats reparse links as links and uses non-following file identity for its volume scope. Native Windows runtime checks remain pending.

The snapshot stores relative paths, node kinds, identities, logical sizes and modification stamps. It contains at most 100,000 nodes; serialized records are bounded to 32 MiB. Invalid provider paths, duplicate nodes, missing manifest parents, unsupported versions and inconsistent states are rejected before execution. Raw Unix names and Windows surrogate spellings use the existing lossless `ProviderPath` representation.

Purge checks the complete remaining tree before mutation. After each progress callback it verifies the recorded container and every ancestor folder again, then checks the node identity, mount and content stamp before removing it. Changed files, unrecorded children, replacement containers and links substituted for folders stop the operation. Links are removed without traversing their targets. A per-node check/remove race remains against external processes that can modify the private container after verification; the cooperating application lease does not exclude those processes. Filesystem mutations use the existing provider boundary; application mutations share the user mutation lease and protect private paths.

## Catalog and interruption

Schema V6 adds `retained_entry`. V7 adds indexed path projections, an exact textual volume key and durable empty-container cleanup tracking. Entries have monotonic identifiers and optional foreign keys into the existing job journal. Live retention records prevent their owning jobs from being pruned. Catalog writes use FULL synchronization. Full-tree verification precedes short checked IMMEDIATE transactions, which recheck observed state, ownership and root identity before a rename or state transition. Purge checks pins again in a short transaction around each individual node removal. Progress callbacks and pause waits never run inside these transactions.

Preparing is committed before container creation. Its identity is committed before the source move. The catalog remains Preparing across the move and post-move verification; Ready is committed only after that snapshot verifies. A correctly named empty container with no committed identity is removed only after checking its source, parent, observed folder identity and mount. An occupied or changed container stays conflicted. An interrupted preparation never starts a new source move: it recognizes a completed move, aborts an untouched preparation, or leaves an ambiguous case for manual inspection.

Restoring commits the target and its parent identity before the move. A collision preserves both files. Reconciliation recognizes the restored object by identity, including user edits made after the move, and leaves replacements untouched. Purging is committed before deletion; a retry permits already removed recorded nodes and folders while still refusing unexpected data. Missing volumes and inaccessible parents do not count as successful deletion.

Restored, Purged and Aborted states are committed before removing the owned empty container. Terminal catalog snapshots remain available; acknowledged terminal metadata pruning remains open. Empty-container cleanup retries are durable, bounded and rotated between entries; an occupied shared holder stays pending until empty. Capture and quarantine do not explicitly sync directory entries. Their interruption guarantees cover process crashes; loss of the latest directory-entry updates during power loss is an accepted remaining limit. The state machine is tested for process interruption.

When the flag and `retain-deletes` are both active, oversized permanent-delete plans show a localized retention warning in the existing required confirmation. Otherwise they use the ordinary permanent-delete confirmation. Only a validated node-count or planned-byte-cap error selects ordinary permanent deletion; other invalid plans and retention settings still refuse. Cancel creates no job and changes no files.

## P35 compatibility and remaining activation

Salvage verifies retention payloads independently. A source from before schema V6 has no retention data to reset. Rejected records, including records whose owner journal cannot be copied, are preserved in the full recovery report with readable original/container/restore-target paths. The persistent notice explicitly identifies retained files requiring manual restoration. Damaged catalog state never authorizes purge.

Remaining work includes periodic maintenance scheduling, acknowledged terminal metadata pruning, Recently deleted, general undo and automatic retained-write rollback. Native Windows runtime verification remains open. Retention is not automatically enabled.
