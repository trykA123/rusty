# P4 · Storage

Status: done (G4 passed 2026-10-15) · Branch: `p4-storage` · After: G3 for merging to `main`

## Goal

`rusty-store` keeps Rusty's data safe from the first day: settings in TOML that are never overwritten when invalid, a session snapshot that draws the first frame without a database, and SQLite databases for user data and caches with migrations and recovery.

## Decisions

- D17 (storage), architecture "No corruption". `rusqlite` with bundled SQLite, latest release.
- Paths come in through a `StoreDirs { config, local }` struct; portable mode only changes how the app builds it.
- `rusty.db`: WAL, `synchronous = NORMAL` except the job journal tables, which commit with `FULL`. `cache.db`: WAL, `synchronous = OFF`, replaced when corrupt.
- Coverage floor `rusty-store = 85` added in W1.
- Atoms that do not need P3's types (W1, W2, W3, W4, W7, W8) may run before G3; W5 and W6 (session) wait for C6. Briefs: [W1](2026-10-15/p4-w1-brief.md), [W3](2026-10-15/p4-w3-brief.md), [W7](2026-10-15/p4-w7-brief.md), [W5](2026-10-15/p4-w5-brief.md).
- The session snapshot is split: `rusty-core::session` (plain data with serde, conversion to and from `AppState`, validation) and `rusty-store::session` (file header, CRC32, postcard, `.bak` fallback). The file magic is `FERRITE-SESSION` (D29).
- The database file is `ferrite.db` (D29), not `rusty.db`; the settings file is `ferrite.toml`.
- `atomic_write` uses `std::fs::rename` (MoveFileExW with replace semantics on Windows) and a hard link or copy for `.bak`, so the crate keeps `#![forbid(unsafe_code)]`; `ReplaceFileW` is not needed.

### Briefs (outline)

- **W1/W2:** temp file in the same folder, flush, `fsync`, replace; on Windows `ReplaceFileW` with `MoveFileExW(MOVEFILE_REPLACE_EXISTING | MOVEFILE_WRITE_THROUGH)` as fallback; previous file kept as `.bak`. Tests inject a failure after the temp write and check the original is intact.
- **W3/W4:** unknown keys are reported, not fatal; a type error keeps the last valid settings in memory and leaves the file untouched; `insta` snapshot of the default settings.
- **W5/W6:** header `RUSTY-SESSION`, format version, CRC32, then the `postcard` body; a bad checksum falls back to `.bak`, then to an empty layout, each step logged; reading the session must take under 5 ms for 3 panes × 100 rows (benchmark test).
- **W7/W8:** migrations are ordered pure SQL strings with fixture databases for every past version; the first migration creates `history`, `frecency`, `tags`, `module_kv`, `job`, `job_step`, `undo`.
- **W9/W10:** keys are bytes; budget in bytes per table; eviction by last access; a corrupt `cache.db` is renamed and recreated.

## Done when

- A crash in the middle of any write leaves the previous data readable (fault tests).
- Settings, session and both databases round-trip; every migration has a fixture.
- `rusty-store` coverage ≥ 85 %.
