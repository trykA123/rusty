# P30 · Copy engine: Auto mode and benchmark

Status: ready · Repo: `<repo>` · Branch: `p30-aN` per atom · Started: 2026-10-19

## Goal

Copies run as fast as Windows allows without giving up any safety. Auto (the default, D22) copies each file with `CopyFile2`, several files at once where the drives can take it, and unbuffered above a size threshold. Standard stays as the one-file-at-a-time fallback. A benchmark measures both against `robocopy /MT` on the same data, and its numbers set Auto's thresholds.

Today every copy is sequential and goes through Ferrite's own read/write loop (`rusty-fs` `local/ops.rs` `copy_file` → `pump`), so server-side SMB copy, block cloning and Windows' own buffering choices are never used.

## Decisions

Final. Workers never reopen them; a worker that finds one wrong stops and reports.

- **D1 — CopyFile2 on Windows.** The local provider's `copy_file` uses `CopyFile2` with `COPY_FILE_FAIL_IF_EXISTS` (the target is always the new `.ferrite-part` temp file), a progress routine that reports bytes and returns `COPYFILE2_PROGRESS_CANCEL` when the cancel token is set, and `COPY_FILE_NO_BUFFERING` when the file size is at or above the unbuffered threshold (D4). Attributes, timestamps and alternate data streams come from `CopyFile2` itself. The returned byte count is the file size reported by the last progress call. Linux keeps the current pump. The safety steps around it (temp name, size check, rename into place, journal) do not change.
- **D2 — Drive classes.** `rusty-fs` exposes `drive_class(&Location) -> DriveClass { Ssd, Hdd, Network, Unknown }`. Windows: UNC or `DRIVE_REMOTE` → Network; otherwise `IOCTL_STORAGE_QUERY_PROPERTY` with `StorageDeviceSeekPenaltyProperty` (no seek penalty → Ssd, seek penalty → Hdd); any failure → Unknown. Results are cached per volume for the life of the process. Linux returns Unknown.
- **D3 — Parallel in Auto.** The job runner keeps the plan order for every step that is not a file copy, and runs file copies whose target folder already exists in a pool of `workers(source, target)` threads: 1 if either side is Hdd or Unknown, 4 for Ssd to Ssd, 8 if either side is Network. A step is journalled done only after its rename into place succeeds; the journal stays crash-safe because each step is independent and `done` is a set of sequence numbers. Cancel stops handing out work and cancels the copies in flight; their temp files are removed as today. On the first failure no new copies start, the copies in flight finish or are cancelled, and the job reports the failed step with the lowest sequence number. Progress adds the bytes of all copies in flight; `current` shows the most recently started file.
- **D4 — Thresholds.** Unbuffered at 256 MiB and the worker counts in D3 are starting values in one `AutoTuning` struct; A5's numbers may change them (logged here), never the code shape.
- **D5 — Mode setting.** `copy.mode = "auto" | "standard"` in `ferrite.toml`, default `auto`, live like every setting. The F5/F6 dialog shows the mode as a small label ("Auto" or "Standard"); changing it per job is a Beta item (profiles).
- **D6 — Benchmark.** `cargo xtask bench-copy <target-folder>` builds three data sets in a source folder next to the target (10,000 × 4 KiB, 200 × 5 MiB, 2 × 1 GiB), copies each with Standard, Auto and, on Windows, `robocopy /MT:8 /NJH /NJS /NFL /NDL`, three runs each after a cold-ish start (the target is removed between runs), and prints a Markdown table of median seconds and MB/s. The owner runs it on the work PC (local NVMe, and the mapped share) and times Explorer and TeraCopy by hand; results go to `docs/perf.md`.
- **D7 — Out of scope.** Parallel and Large files modes, verify options, profiles and rules by destination (Beta).
