# Speed phase · Navo feels instant on a locked-down Windows laptop

Status: planned (starts after OF1–OF8) · Started: 2026-10-28 · Replaces the parked P28 (`plans/2026-10-19-p28-real-pc-startup.md`)

## Goal

Navo feels faster than Total Commander on the owner's Windows work laptop (i7 12th gen, Intel UHD, CrowdStrike and corporate antivirus). On Linux it already feels snappy; on that laptop every file open, write, flush, rename, DLL load and process start costs extra, so the plan removes work from the UI thread and removes work that is not needed at all.

Inputs: `docs/perf.md` (owner-PC numbers), `docs/research/2026-10-28-perf-audit-sol.md`, `docs/research/2026-10-28-perf-audit-gemini.md` (checked; its exe-strip claim is wrong for MSVC), `docs/research/2026-10-28-*.md` (libraries), the UX stress test report (pending).

## Targets (owner's work laptop)

| Measure | Today | Target |
| --- | --- | --- |
| Summon from tray | — | ≤ 50 ms |
| Warm start to first usable | 540–590 ms | ≤ 250 ms |
| Cold start to first usable | 1.7 s | ≤ 800 ms (the rest is antivirus before `main`) |
| Key press to frame, 50k-file folder, 4 panes | not measured | p95 ≤ 16 ms |
| Open a 100k-file folder | not measured | ≤ 200 ms to first rows |

| Private bytes, two panes, idle | ≈ 137 MB | < 80 MB (driver share measured first) |

## Decisions

- SD1 · Measure first. No atom merges without a before/after number on the owner's laptop or the slow-disk shim.
- SD2 · The UI thread never waits on disk, registry, COM, SQLite, clipboard or process start.
- SD3 · Durable data keeps its guarantees: the operations journal and the safety net stay `synchronous = FULL`. Expendable state (history, cache ages, settings echo, logs) is batched.
- SD4 · No speculative work that loads foreign code: the Windows shell menu is built only on right-click or Shift+F10.
- SD5 · New dependencies only from the research shortlist, pinned, permissive licences, behind a measurement.
- Owner questions (open): see the end.

## Risks and rollback

- Resident instance keeps memory while hidden: opt-in setting; Quit is explicit.
- Off-UI sort and filter can show stale rows: every result carries the listing revision; stale results are dropped.
- Batched writes can lose the last seconds of history or cache ages on a crash: accepted for expendable state only (SD3).
- Each atom is one squash commit; rollback is a revert.

## Atoms

Roles: Sol 6.1 high (Codex, api-builder) for backend atoms; Opus 5.5 medium (senior) for SP7 and SP10; Sonnet for light ones. One atom at a time on Opus.

### SP0 — Measure
- **Change:** `trace` cargo feature with `tracy-client` 0.19 + `tracing-tracy` 0.12 (as Zed's `ztracing`). `--trace <file>` writes one JSON line per input: action, key-to-present ms, UI-thread busy ms, disk calls. A `NAVO_SLOW_FS_MS` shim in `rusty-fs` adds latency to every open/metadata/write for local and CI runs. CI perf guards go back to failing builds (size and start-up, `continue-on-error` removed).
- **Check:** a test that the shim delays a listing; `--trace` output parsed by a test; the owner runs the trace build for one work day.

### SP1 — No idle wakeups
- **Change:** instance pipe waits on an event (overlapped I/O, or `interprocess` 2.4.7 named pipes) instead of 200 ms polls; index activity arrives on a channel instead of a 500 ms poll (off when the index is off); drives refresh on `WM_DEVICECHANGE` plus on demand instead of every 2 s; VSync device checks stop while the window is inactive (vendored gpui).
- **Check:** a 60 s idle trace shows no Navo wakeups except VSync of the focused window; drive hot-plug still appears.

### SP2 — Shell menu on demand (done 2026-10-28)
- **Change:** remove start-up warming (`shell_menu/warm.rs`, temp file) and the 300 ms cursor-rest preload; `drive_class` runs off the UI thread.
- **Check:** trace of 20 cursor steps shows no `IContextMenu` and no DLL loads; first right-click latency measured.

### SP3 — Prefetch with a budget (done 2026-10-28; UNC paths count as network)
- **Change:** the 150 ms rest prefetch keeps results in memory only (no `cache.db` write), skips network and removable drives, and stops after N folders per second.
- **Check:** 20 cursor steps over folders cause no `cache.db` writes; entering a prefetched folder stays instant.

### SP4 — Action services off the UI thread
- **Change:** clipboard read/write on an owned worker (no 10 × 10 ms retries on the UI thread); Ctrl+Z query, open, launch, editor and terminal start, `SHGetFileInfo` exe type and companion discovery run on workers with results posted back in order; companions cached after the first probe.
- **Check:** with the slow-disk shim at 50 ms, the longest UI task during copy, paste, undo and F4 stays under 16 ms.

### SP5 — Fewer writes
- **Change:** log through a buffered writer flushed every second and on WARN/crash; cache access ages kept in memory and written with the next eviction pass; settings save reads and parses `navo.toml` once and ignores its own watcher echo; visits batched; session snapshot debounced to 3 s. Journal and safety net untouched (SD3).
- **Check:** trace of 5 minutes of browsing: write calls and flushes per minute before/after; crash-recovery tests still pass.

### SP6 — Start-up
- **Change:** one shared journal connection; checkpoint only at quit; retention maintenance first pass after 60 s; viewer-memory prune deferred; disk-cache warm-up does not block the first frame; fonts beyond the UI pair and tree-sitter grammar registration load on first use.
- **Check:** `--metrics` phases on the owner's laptop; journal opens at start counted in the trace (target: 1).

### SP7 — Large folders
- **Change:** the worker sorts once (keys precomputed there); cache and UI share one `Arc<[FsEntry]>`; sort changes and quick filter build index vectors on a worker with cancellation and listing revision; status totals cached per listing and selection revision; `Arc<Selection>`; only the pane that changed re-renders; row display strings cached per listing revision.
- **Check:** key-to-frame p95 in 50k and 500k folders with 1 and 4 panes; memory per 100k rows; existing selection and filter tests.

- **SP7a (done 2026-10-29):** the 15 ms per mouse move in the owner's trace came from `--trace` forcing a full render per input; removed. Without it, moves inside lists render nothing; hover enter/leave on chrome renders once.
- **SP7b (next):** split `FerriteWindow::render` into cached child views (title bar, one view per pane, F-key bar) so a hover or one pane's change re-renders only that view (~10 files).

### SP8 — Lints L1
- **Change:** the L1 set from `plans/2026-10-27-beta.md` (clone and pass-by-value first), one crate per commit.
- **Check:** `cargo clippy --workspace --all-targets -- -D warnings` with the new lints denied.

### SP9 — Allocator trial
- **Change:** `mimalloc` 0.1.52 behind a feature; kept only if start-up, private bytes and listing time improve on the owner's laptop.
- **Check:** A/B `--metrics` and trace numbers in `docs/perf.md`.

### SP10 — Resident instance
- **Change:** opt-in "Keep Navo running in the tray": closing the last window hides it; tray icon (`tray-icon`, else a `Shell_NotifyIcon` thread) with Open and Quit; a global hotkey (`RegisterHotKey` on its own thread; `global-hotkey` if it fits GPUI's loop); a second `navo.exe` hands off through the existing pipe and exits before loading GPUI. Hidden window keeps its GPU device; idle cost must be zero (SP1 first).
- **Check:** summon-to-usable ≤ 50 ms on the owner's laptop; idle trace while hidden shows no wakeups; Quit releases the profile lock.

### SP11 — PDF helper ready early
- **Change:** start the PDFium helper process a few seconds after start-up idle and keep it alive; hayro stays a later option (`docs/research` and the 2026-10-28 evaluation: no passwords, no resource limits yet).
- **Check:** first PDF page time on the owner's laptop before/after.

### SP12 — Walkers for find and index
- **Change:** benchmark `dua-core` 5.0.1 and `ignore` 0.4.34 against our find walker on the owner's laptop; adopt the faster one for find and index walks (panes keep `FindFirstFileExW` with large fetch, already optimal).
- **Check:** files per second on a 1M-file tree, both drives types.
