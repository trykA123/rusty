# P23 · Performance measured on every push

Status: done · Repo: `<repo>` · Branch: `p23-bN` per atom · Started: 2026-10-17

## Goal

Every push to `main` measures Ferrite's start-up time and memory on Windows and shows the numbers next to the v1.0 targets (roadmap: cold start ≤ 400 ms, warm start ≤ 150 ms, RAM with two panes idle < 80 MB), so a regression is seen the day it lands.

## Decisions

All decided; workers never reopen them.

- **D1 — Measure in the real app.** `ferrite --metrics <path>` (release builds too) writes one JSON file: process start to first frame, first usable frame (both panes listed), named start-up marks from the existing timing spans, private bytes and working set after 5 s idle, peak working set, exe size, renderer/GPU name, Ferrite version and commit. `--metrics` exits the app after writing. It never touches the user's settings or databases: with `--metrics` the app uses a temporary profile folder unless `--profile <dir>` is given. The spike's `--metrics` in `spikes/gpui-b` is the model.
- **D2 — Fixed workload.** Two panes on a generated fixture: one folder with 5,000 files, one with 200 folders of 25 files each, same names every run. The fixture is generated by the CI job, not committed.
- **D3 — CI job `perf-windows`.** After `build-windows`, on every push to `main`: one first run (called "first", the closest a runner gets to cold) and five warm runs; JSON uploaded as an artifact; a Markdown table in the job summary with min/median/max against the targets. The GitHub runner renders in software (Microsoft Basic Render Driver), so frame numbers are not absolute: the job fails only on a regression guard — median warm start more than 2× the target, or private bytes more than 2× the target — and otherwise reports.
- **D4 — Baseline.** `docs/perf.md` keeps the first numbers and a short history (date, commit, median warm start, private bytes); the roadmap links it. The owner's Windows run with `--metrics` is the real reference and is recorded there when available.
