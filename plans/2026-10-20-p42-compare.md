# P42 · Compare and merge

Status: after the alpha. It does not start until the alpha is done, unless the owner says otherwise. Decided (D70); Q2 answered 2026-10-20; Q1 open, architect defaults apply until answered · Repo: `rusty` · Branch: `p42-<atom>` per atom · Started: 2026-10-20

## Goal

The user can compare two folders, two Git refs of one repository (branch, tag, commit, HEAD, index, working tree) or two repositories in Ferrite's two panes, without checking anything out. The user can open any changed pair as a full-window file diff, edit a real side, and copy a file or a hunk to the other side with the old version kept. Then, before 1.0, three-way merge: a branch pair or a conflicted file opens with its merge-base, and the user resolves every conflict before saving. Ferrite replaces Beyond Compare for this work and adds what it lacks: Git refs as folders, an included three-way merge with automatic base, and every write through a plan, a journal and undo. Files of any practical size compare in full in the first version: large text gets a line diff that opens at once and fills in, binary files get a hex diff, and huge files in a folder compare are checked in the background.

## Spec for people

What the user can do, in plain words. The decisions below make it exact.

- **Start a compare.**
  - Right-click → "Compare with other pane" (D46), or Ctrl+K → "Compare with other pane".
  - Ctrl+K → "Compare branches…" picks two refs of the repository the active pane is in.
  - Typing `C:\src\rusty@main` in the path bar opens that branch read-only in the pane, like an archive. Two panes on two refs, then "Compare with other pane".
- **Folder compare lives in the two panes.** Rows line up. A file that exists on one side only leaves a blank gap on the other. Each row has a status colour: same, different, only left, only right, type conflict (file against folder), case conflict (Windows), unavailable (with the reason), and "same after rules" (for example only line endings differ). Rows still being checked say "checking", and the totals say so too.
- **Moving.** Enter on a folder enters it on both sides. Backspace goes up on both. Enter on a file pair opens the file diff. Alt+↓ / Alt+↑ jump to the next or previous difference. Esc clears the filter first, then leaves compare mode.
- **Filters.** All, Differences, Orphans, Same. The usual type-to-filter works on names. `.gitignore` rules apply by default; "Show ignored" brings ignored files back. A user ignore list lives in settings.
- **File diff opens full-window, like F3.** It opens calm (D58): two sides, changed lines tinted. Changed words are marked inside lines that pair up with a similar line on the other side. Ctrl+B opens the list of differences, Ctrl+I the details (encoding, line endings, hashes, active rules), Alt+V the View menu: Simple (line diff), Rich (changes inside a line, syntax colours, the overview strip), Custom. Options: ignore whitespace, line endings, case, BOM. A raw difference that the options hide is still named in the details.
- **Big text files.** Any text file opens in the diff at once, whatever its size. The top lines up within a second; the rest fills in with a progress line, and scrolling never waits. A memory limit in Settings → Compare (default 1 GiB) decides how much detail very large changes get. A part too big for it shows as one changed block, and the status line says so and links to the setting. Ferrite never falls back to "same or different" only.
- **Binary files.** Binary files open in a hex diff: two hex columns, changed bytes tinted, Alt+↓ / Alt+↑ between differences. Files of equal size line up by offset. Files of different sizes line up by content, so an inserted block shows as a gap and the rest stays aligned. Alt+V switches any pair between Text and Bytes.
- **Big files in a folder compare.** Rows show size and time at once. The content check runs in the background, visible rows first, with progress on large rows, and stops at the first difference. "Stop checking" ends it for one row or all rows. Hashes are remembered, so comparing the same files again is instant.
- **Never stuck.** No file can make a compare hang. Each step has a limit; past it, Ferrite shows a simpler result for that part and says so in the details.
- **Editing.** A side that is a real file can be edited. Typing never waits for the diff; the marks update a moment after you stop. Its encoding, BOM and the ending of every line are kept. Save refuses when the file changed on disk since it was read. A Git ref side is read-only. A side over 64 MiB is read-only in the first version; copying hunks and files still works.
- **Copying.** Ctrl+Alt+→ / Ctrl+Alt+← copy the current hunk (in the diff) or the current file row (in the panes) to the right or left. Each copy is one job with a journal. The old version is kept until Ferrite closes; "Restore previous version" brings it back. Folder sync (many rows, both directions, deletes) waits for the delete safety net (D65) and job undo.
- **Git engine.** Settings → Compare → Git engine: "Installed Git" (default), "Built-in (gitoxide)" or "Automatic". Without an installed Git, Ferrite uses the built-in engine and says so once.
- **Merge (before 1.0).** "Merge branches…" or opening a file Git left in conflict shows base, ours and theirs with a result. One-sided changes are taken automatically. A counter shows the unsolved conflicts; Save stays off until it reaches zero. Whitespace-only conflicts resolve in bulk. `ferrite compare` and `ferrite merge` serve `git difftool` and `git mergetool`.

## Decisions

Final. Workers never reopen them; a worker that finds one wrong stops and reports.

- **D1 — Parts and order.** Each part ends in a review, `cargo xtask gate`, Windows CI and a merge.
  1. Part S: facts and spikes.
  2. Part E (engine), Part G (Git) and Part L (large and binary files) in parallel. Each Part L atom waits for the Part E atoms it names.
  3. Part J: copy and save.
  4. Part U: screens. The designer round U0 can run once S3 is done.
  5. Part Y: folder sync. Blocked until D65 and job undo ship.
  6. Part M: three-way merge, before 1.0.
  - Under the about-15-atoms rule the orchestrator may save the parts as `p42a`…`p42h` plans, with these decisions shared.
- **D2 — Components (D13, D62).** Compare is a first-party module with internal Rust interfaces. Dependencies point down.
  - `rusty-compare`: new, GUI-free, no Ferrite UI or store dependency (Skein can adopt it, D40). It depends on `rusty-core` only, plus `imara-diff`, `similar` 3.x, `blake3`, `ignore`, `xxhash-rust` (line keys), `fastcdc` (byte diff) and `ropey` 1.6 (edited sides, D21). `memmap2`, if S4 earns it, lives in `rusty-app` only (D19).
  - `rusty-git`: new, read-only. The `GitSource` trait, both engines, the engine registry.
  - `rusty-fs::git`: the `repo@rev` read-only provider (ProviderId `git`).
  - `rusty-app::compare`: adapters (side sources, hash cache, engine choice) and the background session.
  - `rusty-ui::compare`: pane mode, file diff, later the merge view.
- **D3 — Git engines (D70 item 2).**
  - One trait, `GitSource`, two engines. `CliGit` drives the installed `git`: one long-lived `git cat-file --batch-command --buffer` per comparison session, `ls-tree -r -z -l`, `merge-base`, `diff-tree`/`diff --raw`, `for-each-ref`, `cat-file --filters`. `GixGit` runs `gix` in-process.
  - Setting `[compare] git-engine = "git" | "gix" | "auto"`, default `"git"`.
    - `"git"`: the CLI. Any repository format the user's Git can create reads correctly (Git 3.0 defaults: SHA-256 objects, reftable refs).
    - `"auto"`: gix for SHA-1 repositories with the files ref backend, the CLI otherwise.
    - `"gix"`: gix, with a per-repository fallback to the CLI and a visible note when the format is unsupported.
    - No installed `git`: the default falls back to gix with a notice. A repository gix cannot read then shows "Install Git to compare this repository".
  - The format check reads `extensions.objectFormat` and `extensions.refStorage` from the repository config before choosing (`RepoFormat`).
  - Work gix does not do (filters with drivers such as LFS, worktree status with the stat cache) always goes to the CLI when Git is installed, under every setting.
  - Engines register through an internal engine registry (the module system, D13/D62). A module could add another engine later. The settings page lists the registered engines.
  - Every CLI call: `--end-of-options` before user refs, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `LC_ALL=C`, no console window on Windows. Ferrite never writes into `.git`.
  - The CLI needs Git 2.36 or newer (`--batch-command`). Older Git counts as "not installed" for this choice.
- **D4 — Git is the oracle.** Status between Git sides comes from Git's own change lists (`diff-tree -r -z --raw --no-renames A B`; `diff --raw -z --no-renames <rev>` against the working tree, which uses Git's stat cache and filters). Equal object ids skip content reads. CI checks gix against the CLI on the rusty repository; the paperwing repository runs locally through `FERRITE_ORACLE_REPOS`.
- **D5 — Status model (from Skein).** Every row has a raw status (bytes) and a display status (after rules). "Same after rules" is never hidden as "same". A refresh bumps a generation; a write planned on an older generation, on a "checking" row, on a link, a submodule or an unavailable row is refused. No cap fails a whole comparison; limits are per row and name their reason.
- **D6 — Content check.** Order: kinds, object ids, sizes, cached BLAKE3, then the lockstep read with BLAKE3 alongside (D19), with cancel. Never a whole file in memory for the check. The hash cache is a `content-hash` table in `CacheDb`, keyed by provider, path, size, modification time and file id.
- **D7 — Diff (D70 item 5).** `imara-diff` Histogram for lines, over the whole file in the Whole tier and inside each section in the Sections tier (D8, D16), `similar` 3.x for changes inside a line, only on visible rows, lines over 4,096 characters count as whole-line changes. `rusty-core` stays on `similar` 2.7 for now; two versions are acceptable (D44). S2 confirms the choice first.
  - Pairing (from delta): inside a hunk, consecutive removed and added lines form a subhunk. Lines pair by the smallest edit distance with a greedy pass; a pair whose distance passes 60 % of the longer line stays unpaired (S2 tunes it). Word marks go only inside paired lines; unpaired lines stay whole deletes or inserts and face a filler row. Subhunks over 200 lines per side pair in order (D20).
- **D8 — Text sides and size tiers (Q2: no size wall).**
  - Each side decodes on its own (encoding, BOM, per-line endings); the encoding comes from the first 64 KiB. Binary means a NUL in the first 8,000 bytes, as Git does. Binary pairs open in the byte diff (D18).
  - No size limit. Two tiers, chosen per pair:
    - **Whole:** both sides at most 64 MiB. Sides load into memory; whole-file Histogram (D7). Editing works here.
    - **Sections:** either side over 64 MiB. Sides stay on disk as `ByteSource`s and are read in 1 MiB blocks; the diff runs per section (D16). Hunk copy streams (J6). Free editing waits; the side says "Read-only above 64 MiB; copy hunks or the file".
  - Local files are read with positional reads (`ByteSource::read_at`), not memory maps. Reason: a mapped file that another program truncates crashes Ferrite on Linux (SIGBUS) and on Windows makes that program's truncation fail (log rotation breaks). An open diff view never maps a file. The short folder content check may, under D19's ripgrep rule.
  - A Git blob over 64 MiB streams once into a spool file under Ferrite's cache folder. Spool files are deleted when the view closes and at start-up.
  - A side that changes on disk during a diff restarts it with "Changed on disk, comparing again" (`take_changed`).
- **D9 — Writes (D70 item 4).**
  - A new `Step::WriteFile { target, staged, expect }` writes edited text or an applied hunk. `staged` is a temp file on the target's volume; `expect` is the stamp (size, modification time, BLAKE3) of the version the user saw. A changed stamp refuses the step.
  - Copying from a Git ref uses a source reader for another provider (shared with archive extraction).
  - Before D65 and job undo: copies are one file row or one hunk at a time. Compare jobs keep their held old files until Ferrite closes, and "Restore previous version" brings the last one back. Copies never delete destination-only files.
  - Folder sync (many rows, both directions, recycle) is Part Y and waits for D65 and a job undo command.
- **D10 — Where it lives (D70 item 3).** Folder compare is a mode of the two panes. File diff and merge open full-window on the F3 viewer host. D58 applies: calm open, Ctrl+B, Ctrl+I, Alt+V with Simple, Rich and Custom.
- **D11 — Keys.** Context `Compare` (pane mode) and `CompareView` (file diff, merge). All rebindable (D49), with labels in `compare.ftl`. See the key table.
- **D12 — Editable aligned sides.** S3 decides between A (two editable gpui-kit editors with filler rows, scroll-locked) and B (a read-only aligned view; Enter on a hunk edits that hunk in place on one side). U7 builds the S3 verdict. Either way Save goes through `WriteFile`.
- **D13 — Merge (Part M).** Our own diff3 on `imara-diff`. The replay oracle compares with `git merge-file` on every merge commit of rusty and paperwing. Conflict markers in merge, diff3 and zdiff3 styles are parsed. Save stays off until the unsolved count is zero. Ferrite never stages: after saving a file from an unmerged index, it says "Saved. `git add <path>` marks it resolved" with a Copy button.
- **D14 — Tests in proportion.** Many tests for Git reading, filters, merge correctness and copy safety; few for screens.
- **D15 — Who builds what.** Sonnet `api-builder` for decided backend; Sol 6.1 xhigh (Codex) for backend atoms with many edge cases; Opus `senior` for Git processes, filters, Windows, data safety and hard interaction; Sonnet `ui-builder` for decided UI; Opus `designer` once per view family before its UI atoms; `reviewer-senior` per part; `reviewer-cross` (Sol high) on every job, journal and process-spawning diff.
- **D16 — Large text diff.**
  - **Scan.** Each side is read once, both in parallel. The scan builds the sparse `LineIndex` and the xxh3-64 hash of each line's normalised key. A line is an anchor candidate when its hash falls in 1 of K buckets (K = 32 until S4 sets it) and it has at least 8 non-blank bytes. Only candidates are kept, 16 bytes each.
  - **Anchors.** Candidates unique on each side and present on both match. The longest increasing run of matches (patience) splits both files into section pairs. Anchor lines are compared byte for byte when their section is read; a hash collision drops the anchor.
  - **Sections.** Each pair is read back and diffed exactly with D7's Histogram. A pair over the section cap (1M lines or 64 MiB per side until S4 sets it) re-anchors with a denser sample (K/8, down to every unique line). Then D17 applies.
  - **Progressive.** The view opens at once on the first page of both sides. A provisional diff of the first 4 MiB of each side aligns the top. After the scan, sections diff top-down on at most four workers, the section in view first (`focus`). Arriving hunks never move the top visible line.
  - **Moving.** Next difference jumps to known hunks; past them it shows "Looking further… N %" and jumps when one arrives; Esc stops the wait. Rows are built for the viewport only, from the sorted hunk list and the line index.
  - **Targets**, two 1 GB log files (about 10M lines each, at most 1 % of lines changed):
    - first screen aligned under 1 s;
    - full diff under 4 s warm, under 8 s cold;
    - every frame while scrolling under 16 ms; a jump to any line under 50 ms;
    - compare working memory under 256 MiB.
  - **Assumed Windows PC class** until measured: Windows 11, 8 cores with AVX2, 32 GB RAM, NVMe SSD at 2 GB/s or more, files on a local disk. Warm means both files are in the OS cache. windows-latest (4 vCPU) may take twice as long. S4 measures; the owner checks on a Windows PC.
- **D17 — Memory budget, never a wall.** `[compare] memory-budget-mib`, default 1024, range 256–16,384. It caps the compare engine's own memory for one open diff (section working sets, anchors, hunk list, byte regions), not the OS file cache. Above it, detail drops step by step, per section, never for the whole file. The status line names the step and links to the setting.
  1. **Whole** (D8): whole-file Histogram; changes inside lines in Rich.
  2. **Sections:** the same result in nearly every file; Ctrl+I says "Aligned in N sections".
  3. **Coarse block:** a section pair still over the cap after re-anchoring, or over the budget, shows as one changed block. It keeps exact line ranges and counts, pages both sides side by side, and has no changes inside lines.
  4. **Paged hunks:** when the hunk list passes a quarter of the budget, only sections near the view keep line-level hunks. The rest keep counts and are diffed again when scrolled to (under 100 ms per section).
  - Changes inside a line run on visible rows only, so they cost no budget and are not a step of their own. They are off for lines over 4,096 characters (D7) and inside coarse blocks. A line over 1 MiB offers "Show bytes here" (D18).
  - Equal regions are always aligned, and every changed region has exact line ranges. No step shows "same or different" only.
- **D18 — Byte diff, in the first version.**
  - Binary pairs open in it. Alt+V → Bytes switches any pair to it, and Text switches back.
  - Two hex columns (16 bytes per row, offset, ASCII) built from the F3 viewer's hex rows. Changed bytes are tinted; Alt+↓ / Alt+↑ go to the next or previous region.
  - **By offset** (default for equal sizes): both sides are read in lockstep 1 MiB blocks. Differing ranges closer than 16 bytes merge into one region. Regions arrive top-down.
  - **By content** (default for different sizes): FastCDC chunks (min 2 KiB, average 8 KiB, max 64 KiB) with a BLAKE3 hash each, matched with D16's anchor step over chunks unique on both sides. The gaps are changed, inserted or deleted regions. Regions up to 64 KiB per side refine to exact bytes (`similar` over bytes); larger ones stay region-level with the first differing byte. An insertion shows as a gap and the rest stays aligned.
  - Memory: about 40 bytes per chunk, about 5 MB per GB. Over a quarter of the budget, neighbouring regions merge and keep their counts.
  - Read-only in the first version; the file row copy in the panes still works.
  - **Targets**, two 1 GB binaries: hex view open under 200 ms; all regions by offset under 2 s warm, by content under 4 s warm.
- **D19 — Large files in a folder compare (amends D6).**
  - Size and time first. Different sizes are Different at once, nothing read. Equal size and time show "same size and time · checking". Git sides compare object ids first (D4).
  - Guarantee (2026-10-30): Same means the bytes were equal while read, and each side's size and time matched the listing before the read, and its stamp (size, time, file id) did not change during the read. A change between those checks, or an in-place rewrite that restores size and time, is not detected; no file locking. Git and other compare tools give the same guarantee.
  - The content check reads both sides in lockstep 1 MiB blocks with BLAKE3 alongside. The first differing block ends the check: Different, with the first differing offset. Equal to the end gives Same, and both hashes go to the cache. With one side cached, only the other side is hashed.
  - The scheduler (`queue`) checks visible rows first, then smaller files first. Files up to 64 MiB run on as many workers as the machine has cores, at most 12 (ripgrep's cap). Larger files run one at a time per volume, so USB disks, hard disks and network shares do not thrash. Rows over 64 MiB show progress (bytes checked of size), updated at most four times a second.
  - "Stop checking" ends one row's check or all checks within 100 ms. The row then shows "Not checked (stopped)", a final state: a copy may use it, and its plan says the content was not checked.
  - `[compare] content-check = "content" | "size-time"`, default `"content"`. `"size-time"` never reads content; its rows show "same size and time", never "same".
  - The folder view never waits: navigation, filters, Enter and copies work during checks.
  - I/O follows ripgrep: buffered 1 MiB reads by default, which suit many files. Memory maps only when at most 10 pairs are left to check, on local Windows volumes, and only if S4 shows a gain over 30 %. A map lives for that one check, never for an open view (D8). Linux always reads buffered: a truncated mapped file kills the process there.
  - The first NUL in a buffered block marks the row binary (ripgrep's quit mode). Text rules never apply to it; Enter opens the byte diff.
  - Why: the research reports slow Beyond Compare folder compares on USB and network drives, and Beyond Compare offers timestamp+size, CRC and byte-by-byte as separate methods (`research.md`, Beyond Compare section). Ferrite does one pass that stops at the first difference like byte-by-byte and remembers hashes like CRC, without blocking the view. The research has no evidence about Beyond Compare's large-text or hex compare, so this plan claims no advantage there.
- **D20 — Compare never hangs (from difftastic).** Every diff step has a hard cap and a cheaper fallback, so no input stalls a view or a worker. The caps are named constants in one place, measured by S2 and S4. Ctrl+I names every fallback that ran.
  - Word marks: lines over 4,096 characters (D7), or a pair past `similar`'s 5 ms deadline → whole-line change.
  - Pairing: subhunks over 200 lines per side → in-order pairing.
  - Line diff: `imara-diff` runs in its non-minimal mode, which bounds its cost like Git's. A section or Whole-tier file still running after 2 s on its worker → coarse block (D17 step 3) with the notice. The late result is dropped, and a fresh worker takes the slot (at most two extra per diff).
  - Byte refinement: a region over 64 KiB per side → region level (D18).
  - Syntax-aware diff (D40, after this plan) must use difftastic's caps: sides over 1,000,000 bytes, more than 3,000,000 graph nodes (difftastic's limit, chosen there for about 5 s) or a parse error → this line diff, with a note.
- **D21 — Edited sides diff on snapshots (from helix and ropey).**
  - An editable side's text lives in a `ropey::Rope` (1.6, the stable line; 2.0 is beta). Each edit bumps a version and is kept as an invertible transaction, so undo applies the inverse.
  - The re-diff runs in the background on `rope.clone()`, a cheap immutable snapshot, 150 ms after the last keystroke. A result applies only while its version is current; an older one is dropped. Typing never waits.
  - Whole tier only (D8), under D20's caps. Save writes the bytes of the version on screen (D9).
  - With S3 verdict A, the gpui-kit editor's buffer feeds the rope edit by edit. If S3 finds the editor exposes a cheap snapshot itself, that replaces the rope.
